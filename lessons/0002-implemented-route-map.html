PFBTD · Rust 路线 · Lesson 02

从一次请求看懂整个系统

本次实现已经把客户端、HTTP 适配层和业务状态连成一个可运行闭环。以后排查问题时，可以沿着这条链定位。

请求链路

命令行输入
  ↓
client-sync：把命令转换成方法、路径、JSON、Bearer token
  ↓
HTTP/1.1
  ↓
server-async/http.rs：读取请求、限制请求体、解析 JSON
  ↓ spawn_blocking
server-async/lib.rs：校验身份、锁住共享状态、执行业务
  ↓
{"data": ...} 或 HTTP 错误状态

已经完成的模块

  • 客户端输入：单独一行 . 结束；\. 表示正文中的单独句点；空行和 Unicode 保留。
  • 公开接口：GET /ping、POST /echo、注册和登录。
  • 受保护接口：文本上传、覆盖、读取、列表、删除、退出和注销。
  • 身份状态：每个用户只有一个 Token；重新登录替换旧 Token；注销删除用户和文本。
  • 过期：默认 300 秒，可用 --token-ttl-seconds 配置；过期不会被普通操作续期。
  • 并发：Mutex 保护用户表；登录计算密码时不持有锁；异步服务端用 spawn_blocking 隔离 PBKDF2。

三个重要设计理由

  1. 先把业务放在 lib.rs，让它可以脱离网络直接测试；HTTP 层只负责适配。
  2. Token 检查、文本操作和注销在同一把状态锁的保护下完成，避免检查通过后被另一个请求插入中间态。
  3. 登录先复制盐、摘要和账号代数，释放锁后计算密码，再回来确认代数仍相同；这样注销并同名重注册不会让旧登录写入新账号。

验证命令

cd projects/rust/client-sync
cargo fmt -- --check
cargo check --locked
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo build --release --locked

同步服务端和异步服务端目录分别执行同样的命令。遇到错误时，先看它属于客户端、HTTP 适配、业务状态还是异步边界。
