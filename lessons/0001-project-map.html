PFBTD · Rust 路线 · Lesson 01

先建立地图，再写第一行代码

这一课的胜利标准很小：你能说清楚三个 crate 各自负责什么，以及为什么我们要在每个目录单独运行 Cargo 命令。

1. 你刚刚验证了什么

本机工具链是 Rust 1.98.1 / Cargo 1.98.1。三个项目的起始测试都通过：

  • client-sync：1 个集成测试通过。
  • server-sync：7 个业务/HTTP 测试通过。
  • server-async：6 个业务/HTTP 测试通过。

2. 三个 crate 的职责

crate 可以先理解成一个独立的 Rust 包：有自己的 Cargo.toml、锁文件、源码和测试。

  • client-sync：命令行用户；负责收集输入、发 HTTP 请求、保存本地 token。
  • server-sync：同步业务过渡层；先练业务规则、状态和锁，不引入 async/await。
  • server-async：最终服务端；请求处理异步，但密码计算等阻塞工作必须移出运行时线程。

3. 为什么每个目录单独运行

仓库没有 Cargo workspace。每个 crate 都是独立的依赖图和锁文件；cargo test --locked 要求清单与锁文件一致，避免“今天能编译、换机器就变样”。

工作流原则：先改一个小行为 → 写测试 → 跑测试 → 看差异 → 再提交。测试不是最后才做的验收，而是我们每一步的反馈。

4. 你的第一个决策

我们可以按两种方式推进：

  1. A：客户端优先（推荐）。先完成一个真实闭环：输入 → HTTP → 响应 → token；反馈快，能先建立 HTTP 心智模型。
  2. B：服务端优先。先实现协议和状态，再补客户端；适合想先深入 Rust 业务建模的人，但前期反馈较慢。

我推荐 A，因为你的目标是降低认知负荷，同时保留关键决策；先完成一个闭环能让后续每个接口都有参照。
